# AFService Map v0.68.0 — Backend do monitoramento SNMP

Backup/ponto de rollback desta rodada: tag `v0.67.8`. **Tem migration**
(`apps.snmp_monitoring.0001_initial`) — roda automaticamente no `apply`.

Esta versão implementa o backend combinado com o Gemini pra integrar a
stack de monitoramento (Telegraf + InfluxDB, já rodando em produção) ao
Django/Celery. **Não há UI ainda** — nada muda visualmente no mapa nem
nas telas de equipamento nesta rodada. Isso é intencional: as telas de
cadastro (mapa e lista de equipamentos) ficam na área que o ChatGPT está
trabalhando ativamente, e vamos esperar a rodada atual dele terminar
antes de adicionar os campos de SNMP nos formulários, pra não editar os
mesmos arquivos em paralelo.

## Revisão da proposta original

O Gemini mandou dois scripts de prova de conceito. Adaptei o que veio
antes de virar código real, por três motivos:

1. **O token do InfluxDB veio em texto puro no script** — já deve ser
   tratado como comprometido. **Precisa ser rotacionado no InfluxDB antes
   de configurar `INFLUXDB_TOKEN` no servidor.** Nenhum segredo fica no
   código: só variável de ambiente (mesmo padrão do `FIELD_ENCRYPTION_KEY`
   e dos tokens do IXCSoft).
2. **O script chamava `docker restart monitor-telegraf` a partir do
   processo web.** Isso exigiria expor o socket do Docker pro container
   `web` (que recebe requisição da internet — um jeito direto de dar
   controle do servidor inteiro pra quem achasse uma falha no app), e
   derrubaria a coleta de todas as empresas a cada equipamento novo
   cadastrado por qualquer uma delas. Troquei por `SIGHUP` (recarrega a
   config sem derrubar o container) disparado só pelo `worker` (nunca
   pelo `web`), via Celery — nunca de dentro de uma request HTTP.
3. **Faltava validação do IP/community antes de gravar no `.conf`.** Uma
   community com aspas ou quebra de linha poderia injetar diretivas
   arbitrárias no Telegraf. Adicionada validação (`ipaddress.ip_address`
   pro IP, charset restrito pra community) antes de qualquer gravação.

Também descobri que `apps/olt_integration/models.py` **já tinha** os
campos de SNMP pra OLT (`snmp_community_encrypted`, `snmp_version`,
`status`, `last_poll_at`...) de uma rodada anterior — só nunca foi
implementada a coleta de verdade. Por isso o modelo novo
(`SNMPMonitoringProfile`) segue o mesmo padrão de criptografia, em vez de
reinventar do zero.

## O que foi criado

- **`apps/snmp_monitoring/`** (app nova, isolada — não mexe em nada do
  `apps/network_map`, que é a área do ChatGPT):
  - `models.py` — `SNMPMonitoringProfile` (IP, porta, community
    criptografada, intervalo de coleta, `influx_id` — identificador
    estável e opaco usado como tag no InfluxDB e no nome do `.conf`,
    nunca o ID interno do banco).
  - `conf_templates/snmp_universal_status.conf` — o template do Telegraf,
    agora versionado no repositório (antes só existia solto no
    servidor).
  - `services.py` — validação de IP/community, renderização do `.conf`,
    escrita atômica (grava em `.tmp` e troca com `os.replace`, pra o
    Telegraf nunca ler um arquivo pela metade) e remoção.
  - `docker_control.py` — `SIGHUP` no container do Telegraf via SDK do
    Docker.
  - `influx_client.py` — consulta o InfluxDB pelo `influx_id`, retorna
    `{"porta": "UP"|"DOWN"|"OUTRO"}`.
  - `tasks.py` — `apply_snmp_monitoring_profile` (gera/atualiza o `.conf`
    e recarrega o Telegraf, roda em background via Celery),
    `remove_snmp_monitoring_profile` (idem pra remoção) e
    `poll_snmp_status` (task periódica: consulta o InfluxDB de cada
    equipamento monitorado e atualiza `NetworkElement.status` — o mesmo
    campo que já define a cor do marcador no mapa).
  - `signals.py` — salvar/apagar um `SNMPMonitoringProfile` dispara as
    tasks automaticamente (nada de lógica de infraestrutura dentro do
    ciclo de request/response).
  - `admin.py` — cadastro básico pelo Django Admin (`/admin/`), único
    jeito de criar um monitoramento SNMP por enquanto, até a tela própria
    ser feita depois do ChatGPT.

- **`config/settings.py`**: app registrada, variáveis de ambiente
  (`INFLUXDB_URL`, `INFLUXDB_TOKEN`, `INFLUXDB_ORG`, `INFLUXDB_BUCKET`,
  `SNMP_TELEGRAF_CONTAINER`, `SNMP_CONF_DIR`), tarefa `poll-snmp-status`
  no `CELERY_BEAT_SCHEDULE` (a cada 2 minutos).

- **`docker-compose.yml`**: variáveis de ambiente do InfluxDB
  disponíveis pros três serviços; **só o `worker`** ganhou acesso ao
  socket do Docker (`/var/run/docker.sock`) e ao volume
  `equipamentos_ativos_snmp/` (o mesmo caminho que já era usado
  manualmente, agora escrito pelo Django).

- **`requirements.txt`**: `influxdb-client` (já tinha entrado na v0.67.6)
  e `docker` (SDK Python, pra mandar o `SIGHUP`).

## Configuração necessária no servidor (antes de usar)

1. **Rotacionar o token do InfluxDB** (o antigo está comprometido).
2. Definir as variáveis de ambiente no `.env` do servidor:
   `INFLUXDB_TOKEN`, e conferir se `INFLUXDB_URL`/`INFLUXDB_ORG`/
   `INFLUXDB_BUCKET`/`SNMP_TELEGRAF_CONTAINER` batem com os nomes reais
   usados no `docker-compose-monitor.yml`.
3. **Rede Docker**: o `worker` precisa alcançar `monitor-influxdb` pelo
   nome do container (`INFLUXDB_URL` default é
   `http://monitor-influxdb:8086`). Isso só funciona se os dois
   `docker-compose` (o deste projeto e o do monitoramento) estiverem na
   mesma rede Docker — confirmar isso com quem montou o
   `docker-compose-monitor.yml`; senão, ajustar `INFLUXDB_URL` pra um
   endereço que o `worker` realmente alcance.
4. **GID do socket do Docker**: o `docker-compose.yml` usa
   `group_add: ["999"]` pro worker conseguir usar o socket (o container
   roda como usuário não-root, UID 1000). Rode
   `stat -c '%g' /var/run/docker.sock` no servidor — se não for `999`,
   troque o valor no `docker-compose.yml` antes do `apply`.
5. Confirmar que `equipamentos_ativos_snmp/` (pasta que já existe no
   servidor) é o mesmo caminho montado no `docker-compose-monitor.yml`
   pro Telegraf ler — senão o Telegraf nunca vai ver os `.conf` gerados
   pelo Django.

## Fora do escopo desta rodada

- Nenhuma tela nova (cadastro de SNMP fica só pelo `/admin/` por
  enquanto).
- Nenhum alerta automático (`AlertEvent`) ainda — hoje só atualiza
  `NetworkElement.status`, que já reflete no mapa. Ligar isso ao motor
  de alertas é trabalho futuro (o modelo de alertas atual só cobre
  CTO/OLT/ONU/rota, não elemento genérico).
- OLTs continuam com seu próprio mecanismo (`apps/olt_integration`, já
  existia) — este app novo é pra equipamento genérico (switch, rádio,
  AP, etc.).
